# Design

## The problem

AI coding agents write plausible code fast. What they don't produce is *evidence*.
The usual answer is tests, but a test checks one input, and an agent that writes
both the code and the tests tends to write tests that agree with the code.
Requirement-tracking systems help with the other half: they record *what* the code
is for and *which* code implements it, so a change to one side is noticed on the
other. But they can't tell you whether the aim is actually met. The link from
an English sentence to the code is traceability, not truth.

telic's aim is to close that loop mechanically, with good *locality* (evidence
lives next to the code it is about and is invalidated precisely when that code
changes) and good *legibility* (every claim and every failure points at source
lines a person can read in ten seconds).

```
aim  ──formalize──▶  contract  ──verify──▶  evidence
  ▲                        ▲                      │
  │                        └──── telic gaps ──────┤  (is the contract strong enough?)
  └──────────── aim status is computed from ───┘
```

## Principles

**1. Contracts are code, in comments.** Following C0 (15-122), contracts are
host-language expressions in `@`-comments. They are legible to anyone who can read
the function, cost nothing at runtime, and can be switched on when you want them:
`telic run`, or the pytest plugin, compiles them into runtime checks, just like
C0's `-d`.

**2. One small IR, many languages.** Frontends lower Python (via `ast`),
TypeScript (via the official compiler API) and Rust (via tree-sitter) into one
small imperative IR. Operators
that differ between languages are different IR operators: Python's `//` is
`floordiv`, JavaScript's `%` is `tmod`, Rust's `/` on integers is `tdiv`,
`round` is `round_even`, and `Math.round` is `round_up`. Nothing is shared by accident. What the IR models exactly, it
models exactly. What it cannot (a library call, an untyped value) becomes
opaque: an uninterpreted value or call with a conservative effect. The
assumption that makes it usable ("does not raise") is recorded and reported.
Verification extends to the whole program. It doesn't stop at the edge of the
modelled subset, and unchecked code can never make a false claim provable.

**3. Modular obligations give locality.** Verification conditions are generated by
symbolic execution with branch merging. A call is checked against the callee's
*contract* (prove its `@requires`, assume its `@ensures`), never its body. So a
function's proof depends only on its own body and on the contracts it calls
(for a method call through a base class, the contracts of every override). Each
obligation is content-addressed by its exact formula; the cache (and Lean sidecar
staleness) follows automatically. Edit a body and only that body is re-verified;
edit a contract and its callers are re-verified; move a file and nothing changes.

**4. Evidence is a ladder, and every rung is cross-examined.** Each obligation is
discharged by the cheapest oracle that can decide it, and no single oracle is
trusted blindly:

| rung | oracle | cross-examination |
|---|---|---|
| inference | Houdini over candidate invariants/measures | every inferred fact is itself proved |
| SMT | Z3 (two phases: definitions only, then + theory lemmas) | counterexamples are **executed** in the real runtime |
| Lean auto | `omega`, `grind`, `simp` … on the same formula | `#print axioms` audit |
| Lean agent | an agent writes the proof, Lean's errors are fed back | same audit; stored next to the code; statement re-derived every run |
| testing | contract-checked fuzzing with shrinking | reported as testing, never as proof |
| judgment | an oracle (builtin rules, a classifier such as Jev, or an LLM) answering typed questions | labelled with who answered and how sure; only ever about coverage and drafts, never a verdict |

A solver model the real program cannot reproduce is not reported as a bug. It
means an invariant is too weak, and telic says so. The theory lemmas Z3 is given
are proved in Lean (`telic/lean/Theory.lean`). The arithmetic semantics are
differentially tested against CPython and Node, and Rust counterexamples are
compiled with `rustc` and run.

**5. The contract is attacked too.** A proof certifies code against a spec, and a
weak spec certifies wrong code. `telic gaps` mutates proved code and re-verifies
it. A surviving mutant that demonstrably differs from the original, shown as a
diff plus an input, is exactly the missing `@ensures`. Besides small operator
mutations, it deletes guard, validation and authorization checks, and with
`--llm` a model writes realistic bugs too. For what survives, it proposes a
stronger `@ensures` and verifies it against the original and the mutants
before showing it.
A safety aim ("shall never") is checked the same way from the other side: if
a stub that returns at once meets all its lemmas, it is `vacuous-risk`. This
is how telic narrows the gap between the English aim and its formalization,
which no verifier can close alone.

**6. Strict where it counts, silent where nothing is claimed.** Following
Rust and OCaml rather than Python, a function that makes a claim is held to
it: with a contract, falling off the end of an `-> int` function, a reachable
`raise` you didn't declare, and a loop that might not terminate are all
errors. A list alias the model can't track, or a `number` used as an index
when telic can't show it's an integer, is an error anywhere. Code without a
contract is checked only for crashes (a Rust panic always counts), because an
intentional `raise HTTPException` or a `while (true)` reader is not a bug.
Every finding comes with a line number and, where possible, a real failing
input.

**7. Requirements are words, and are never proved.** An aim is one EARS
sentence. The contract clauses that cite it are its lemmas, and those are
proved; the aim is only "backed". Whether the lemmas cover the sentence is
recorded by a person (`--accept`) or judged by an oracle (`--judge`), both
pinned to a digest of the sentence and the lemma set. telic never pretends
facts fully specify a system.

## Architecture

```
  Python ──── frontend/python.py ───┐
  TypeScript ─ frontend/ts/*.mjs ───┼─▶ ir.Module ─▶ program.py (call graph, overrides,
  Rust ────── frontend/rust.py ─────┘                SCCs, definitional fns, heap writes)
                                                        │
                                   infer.py (Houdini) ──┤
                                                        ▼
               vcgen.py (Python core)  or  core/ (OxCaml engine, via engine.py + irjson.py)
                          symbolic execution ─▶ Obligation(hyps ⊢ goal), terms in logic.py
                                                        │
                  ┌──────────────────────┬──────────────┼──────────────────┐
                  ▼                      ▼              ▼                  ▼
            smt.py (Z3)          lean.py (Lean 4)   equiv.py        gaps.py (mutants
                  │                      │         (@mirrors)        + equiv)
                  ▼                      ▼
        replay.py: run the real code   sidecar proofs, agent loop,
        (CPython / Node / rustc),      axiom audit, staleness
        fuzz + shrink
                  └──────────────┬───────────────┘
                                 ▼
          checker.py: verdicts, receipts ─▶ render.py / html.py / --json
                                 │
          aim.py (EARS, links, status) · propose.py + phrase.py (facts, drafts)
          ledger.py (CI ratchet) · oracle.py (judgments, never proof)
```

The OxCaml engine generates and solves obligations in parallel (one Z3 per
domain). It covers everything the Python core models, a function it cannot
handle falls back to the Python core, and `tests/test_engine.py` requires the
two to agree obligation by obligation.

* **`logic.py`** is a small many-sorted term language with folding smart
  constructors. Both Z3 and Lean are *renderings* of the same terms. Integer
  division is Euclidean everywhere, the one convention Z3 and Lean share. Lists
  are `(array, offset, length)`, so slices cost nothing.
* **Pure functions become definitions.** A loop-free, mutation-free function is
  also a logical function, usable inside specs (`ensures result == fib(n)`). Its
  definition is guarded by its precondition, which keeps recursive definitions
  total and well-founded, and its `@ensures` become lemmas everywhere outside its
  own recursion group.
* **Termination** is an obligation: loop variants and recursion measures are
  checked, and inferred when omitted.

## Cross-language equivalence

`@mirrors` runs both function bodies through the same symbolic executor over
shared input symbols. For loop-free code the question "is there an input where
both preconditions hold and the results differ?" is one SMT query. A model is then
executed in *both* runtimes before it is reported, and telic names the likely
culprit (banker's rounding versus round-half-up, floor versus truncating division,
modulo sign) by comparing the operators each side actually uses. Code with loops
falls back to differential testing, labelled as such.

## Prior art, and what's different

* **C0** gave the contract syntax and the "contracts are free until you ask for
  them" model.
* **Dafny, Why3, Viper/Nagini, Verus, F\*** are the lineage of VC generation
  and modular verification. telic applies it as a *postprocessor* on languages
  people already vibecode in, rather than asking them to adopt a verification
  language.
* **Requirement-tracing tools** and the EARS templates gave the aim layer:
  requirements as sentences, with links in both directions to what implements
  them. telic adds proof status to the links.
* **CrossHair** (Python) and bounded symbolic execution find counterexamples
  well; telic aims for proofs and uses execution to *confirm* its
  counterexamples.
* **Lean** is the backstop: when automation fails, a real proof assistant with a
  small kernel decides, and agents are now good enough to drive it.
* **Rust / Haskell / OCaml** set the bar for strictness: totality, no silent
  `None`, no unchecked partiality.
